# Catalog Health

The existing catalog status route (`#catalog-status`), linked as Catalog Health in navigation, uses the same federated records as the Explorer. No separate database, frontend framework, or live dashboard requests are required. Discovery JSON is a versioned artifact; optional `healthHistory` version 1 carries a complete successful snapshot and its comparison.

Discovered counts deduplicate stable IDs and canonical endpoints. Publisher counts use actual record publishers; absent publishers appear as Unknown publisher. Verified totals count fresh successful structural checks within the latest completed nonfailed cycle, not discovery totals or the legacy curated `verified` date. Never-checked or malformed timestamps are Not checked. Recent timestamped failures are Failed; completed checks older than `config/verification.json` freshnessDays (seven days) are Stale, with their underlying result preserved. Missing title, publisher, source link or field schema requires attention. Attention counts each affected record once. A publisher's last checked time is its latest recorded dataset attempt, not proof that every dataset was checked.

See [dataset verification](dataset-verification.md) for the persisted result schema, seven-day freshness policy, safe errors and cache rules. The existing refresh inspects ArcGIS layer responses and field schemas; discovery adapters inspect supported external resources. A successful HTTP response or valid-looking URL alone does not qualify. Safe failure explanations are retained with attempt timestamps; network, authorization, missing endpoint and unsupported schema errors remain available in source diagnostics. Discovery scans can fail before a dataset is identified: those errors appear in publisher scan details, not invented dataset failures. Structural verification does not establish record accuracy, completeness or freshness. Browser access audits in access.json are separate from server endpoint checks.

Discovery and verification run together daily at 04:17 America/New_York in `.github/workflows/discovery.yml`, or manually with `npm run discovery:refresh`. Scans have explicit budgets and may remain partial. The curated package catalog is generated separately with `npm run catalog:generate`; it has no independent daily schedule.

Only fully successful complete refreshes establish health snapshots, using current scan results plus curated records and stable IDs. Metadata comparisons use SHA-256 fingerprints and omit verification times and errors, keeping the artifact compact. Two successful snapshots are needed for added, removed and changed counts. Failed or partial refreshes preserve the prior snapshot and comparison. Removed means absent from that complete supported scan, not proof a source was deleted. The browse catalog deliberately retains prior entries for continuity. Legacy lastSuccessfulRunAt means some checks succeeded, so it is not used as the complete successful refresh date. Until the new history exists, that date is Not recorded and changes are Not yet available.

Coverage is limited to configured publishers, supported machine-readable endpoints, and scan budgets. Some publishers offer no machine-readable inventory. Metadata quality varies, and availability and source updates can change between jobs. See publisher scan diagnostics for actual limits and failures.

For failed jobs, inspect the workflow logs and discovery-report artifact, then publisher scan details and original errors. Check credentials, endpoint availability, response schema and configured allowlists; rerun the refresh and validation commands after fixes. No history is inferred from a failed process. Published timestamps describe the published artifact, not unpublished workflow attempts. Same-day unchanged reruns remain in workflow artifacts.

To add a publisher, update `config/portals.json` with its supported platform, authoritative evidence, publisher, jurisdiction and explicit service prefixes. Follow `docs/federation.md` for adapter support and allowlist requirements. Run discovery refresh, discovery validation, catalog validation and tests before publication.

## Local build note

The production frontend uses the existing Vite build. On Windows, OneDrive-backed source files may appear as symbolic links to Node's directory enumeration; Wrangler's Pages route scanner skips them and reports "No routes found". A byte-for-byte copy of functions, src, public and config into ordinary temporary directories compiles successfully with the same Wrangler Pages Functions command. The Linux deployment workflow uses a normal checkout. No deployment or infrastructure changes are required for the dashboard.
